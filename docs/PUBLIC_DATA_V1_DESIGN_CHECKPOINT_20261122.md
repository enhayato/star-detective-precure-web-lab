## 1. 产品目标及收录边界｜已认可方向

- 面向普通《名探偵プリキュア！》粉丝，帮助他们发现「原来别的地方／家附近还曾经安排过这样的活动」，回顾 2026 年活动足迹；**不是**产业研究库镜像、实时票务／预约／导航站，不承诺全国穷尽收录。
- 优先收录有明确公众参与体验的活动：角色秀、握手/击掌会、Staff Talk、演唱会、主题展、主题咖啡厅、快闪、解谜、地方体验等；有明确参与机制的线上活动可以收录。
- 普通商品发售、广告投放、合作新闻不因属于商业联动就自动成为 Activity；同一企划中的促销与独立地方特别活动必须区分。
- **初步类别候选（尚未最终批准词表）**：角色活动／演出与音乐／交流与特别上映／展览与快闪／主题餐饮／参与型活动／线上参与／其他。正式分类边界、跨类别及标签机制留待敲定。
- 核心版权方参与不自动升为最高展示优先级；外部企业举办也不自动降低。优先级仅用于浏览，不代表活动质量、历史价值或官方评价。

## 2. 逻辑层级与纪念册｜已认可方向

- `Activity`：粉丝可识别的活动主题／主档，不要求与研究库 Project 一对一。
- `Occurrence`：具体地区、场地及其有效日程的**举办实例／会场档期**；不得误解为主办公司。
- `Session`：需要区分时才设置的个别场次。普通主题展每日开放不自动产生每日 Session。
- `Announcement`：首次公告、追加、改期、取消等历史节点；`Source`：为具体公开断言提供的可追溯来源；`Media`：独立审核可再利用条件的可选素材。
- 全国共通参与机制不应伪造 47 个地方 Occurrence；允许与 Activity 关联的「全国共通信息」独立表达。若有被证实的某地特别场次，则建立该地 Occurrence。
- **每个 Activity 原则上一份纪念册**；从地图进入定位相关地区／Occurrence，从日历进入定位日期及 Session，从档案进入默认看整体。纪念册具体 URL 参数（例如 `occ`、`session`）尚为技术候选。
- 同一 Activity 同一天的多个场次：预览**合并为一张可展开卡片**，展开列出场次；同一天多个场地，展开后按会场分组。独立身份显著不同的特别活动可另立 Activity，并保留关联。
- 已有演示详情直链 `event.html?id=sample-staff-talk-20261015` 及 `from=calendar|map|archive`、筛选参数和返回体验须兼容；旧演示 ID 不得未经审查暗中映射至新正式活动。

## 3. 证据与事实状态｜已认可规则

**必须分开「举办安排状态」与「实际举行证据状态」。**

- 有可靠官方／主办方原始公告明确活动、日期、地点等，可收录为「有正式举办安排」；无需强制获得事后现场报道。
- 事后报道或其他可靠材料确认举行，才使用「已确认实际举办」；**没有发现取消公告 ≠ 已确认举行**。
- 已确认取消／延期／改期，须有可支持该变更的证据；不能因为没有 SNS 照片就认定取消。
- 来源等级、是否实际阅读正文、是否支持某个具体字段及图像再利用权彼此独立。机器校验通过不代表事实已经人工核准。
- 面向普通粉丝可用轻松日文，如已公告但未确认「こんなイベントが予定されていたんだって！」、已举行「こんなイベントが開催されていたよ！」；轻松措辞不能混淆证据强度。具体用词待 UI 细化。
- 公开地图四色**不编码**核查等级；资料状态在预览及纪念册次级文本中说明。

## 4. 取消、延期、改期与地图｜已明确认可的行为

| 当前筛选下的地方记录 | 地图表现 | 日历／预览／纪念册 |
| --- | --- | --- |
| 有已确认举办或可靠公告、未独立确认实际举办的**有效安排** | 正常四色随机高亮＋金边 | 正常卡片；逐项准确标注事实状态 |
| **仅有已确认取消**记录 | 深灰，无正常高亮；低调灰色历史角标 | 灰色 `開催中止` 卡片，原定日期/会场/取消依据仍可查 |
| **仅有延期未定／改期前历史** | 深灰，无正常高亮；低调灰色历史角标 | 灰色变更记录，指向后续安排（如已知） |
| 取消与延期／改期历史共存，没有有效安排 | 深灰＋低调历史角标；具体状态进预览区分 | 不用多个夸张图标堆叠 |
| 有有效安排，同时还有取消／改期历史 | 地图正常高亮，不因部分取消降灰 | 预览保留灰色历史／取消场次，正常安排优先 |
| 无任何符合筛选的收录记录 | 普通深灰，无角标 | 明确「暂无已收录」，不说「从未举办」 |

- 取消活动**仍属于历史收录**，不能删除；仅不触发代表有效参与机会的地图高亮。
- 改期：**旧日期保留灰色「日程変更」历史，新日期正常展示**，两者关联到同一纪念册／Activity；多次改期应可追溯，不重复创建 Activity。
- 延期未定：保留旧安排，不推测新日期；如果后来证实最终取消，更新当前状态但不擦去延期史。
- 部分会场／Session 取消只影响相应范围，不得把整个巡回活动统一设为取消。
- 常规固定休馆日不自动制造「取消活动」记录；若公告后某次预定开放被取消，应保留对应变更史。
- 角标只是历史信息提示，不是独立点击按钮；地区方块继续可点击，并为图标提供文本或无障碍语义。角标精确位置/大小未锁定。

## 5. 有效日期、预览与排序｜已认可原则＋待细化

- 日历和现有地图依据**经证据支持的有效参与日期**，不能把 `start/end` 中间所有日期自动视为开放；周末限定、固定休馆、临时停办、跨月／跨年都需正确处理。
- 原定已取消／改期日期仍可作为**历史记录**供检索和显示灰色卡片，但不成为有效举办日期。真实举办结束日不得为迁就 2026 年日历被改写为 `2026-12-31`。
- 地图预览先分区：**当地活动优先**，全国共通参与信息放在当地列表之后的独立可折叠区；全国新开始的促销不能挤到当天当地角色秀之前。全国共通信息本身不点亮各县，已确认地方特别场次例外。
- 当地活动的既定排序方向：**以选中日为基准，开始日期越近越前 → 人工审核的展示优先级 → 日文五十音读音排序键 → 稳定 ID**；同日有效场次在展开区内部按真实时间排序。这里的「开始日期」指相关举办实例的开始，而不是把主题展每次周末开放虚构为一项新活动。
- **待细化：**「新开始 vs 重新开放」混合、日期范围查询的排序基准、准确日文读音键、不同日内场次状态顺序及仅月份精度的处置。
- 单日或单地区可能有大量记录，预览用紧凑折叠结构；手机标题允许两行。分页／首次显示条数未决定。
- 展示优先级采用客观分类建议＋单人维护者最后确认＋简短理由＋可纠正记录。证据不足时中性处理、不直接认定低价值。**「重点展示／常规展示」两档是当前推荐草案，尚未单独最终确认词表和触发阈值**；无需招募复核人员作为发布前置条件。

## 6. 计数规则｜已明确认可

- 用户所见「X 项活动」按当前日期、地区、类别等**筛选后的不同 `activityId` 去重**。不同场馆／场次、连续开放多日、公告变更不重复制造 Activity。
- 全国一个巡回 Activity 可全国计 1 项，东京／大阪各自筛选时也各计 1 项；各地区数字求和不必等于全国去重后的数字。
- **已取消活动计入活动档案总数**，同时单独显示其中「全部取消」的活动项数；部分取消仍计一次活动，但使用「一部開催中止」等标记。
- 「全部取消」须按**当前筛选范围**汇总：仅当该范围内相关安排均有可靠证据确认取消，才计入取消活动数；东京正常、神奈川全取消时，两地区显示不同取消数量。
- 延期未定及改期前历史不应误算为「已取消」，实际发生未获证也不应误算为「已确认举行」。
- 同一 Activity 旧日期＋新日期落在同一个月时，月度总数去重为 1；**各单日活动数相加不等于整月总数**。
- 地图高亮依据是否存在至少一项**符合筛选的有效非取消举办安排**，与活动总数或全部取消数不是同一个指标。
- **尚需测试**：在范围内同时命中旧改期记录和有效新日程、仅有状态未定记录、同日跨会场与全国共通信息时，计数对象及文案要一致。

## 7. 数据文件架构：方案 C｜已认可「先按此方向推进」，物理细则未锁定

### 为什么改变上一轮单一 JSON 推荐

本阶段起初考虑 `events-public.json` 单文件（方案 A）；看到研究库实际规模后重新评估：Projects 第一列非空 ID 182、Milestones 699、Sources 564、文件 Drive 元数据约 970 KB，且调查仍在继续。**这些数不是网站 Activity 数，也不能换算成 JSON 网络体积**，但足以表明一开始就把完整来源／历史详情送到每个日历或地图访客并不理想。

维护者已同意**优先方案 C：轻量公开索引＋按需获取详情**，同时保留静态 GitHub Pages、无服务器、人工审核发布的路线。不要把它倒写成已批准精确 schema、文件名或拆分阈值。

### 暂定实现边界

- `catalog.json`（候选名）：日历／地图／档案所需的轻量活动索引——公开 ID、名称、类别、地区、有效日程、状态、计数/排序必需数据、场次最小摘要。
- `details.json`（候选名）：进入纪念册才读取的详情——完整说明、会场和场次扩展、公告修订史、对外来源、已确认许可的素材信息。**若详情仍是一个整体文件，点开一份纪念册仍需下载全部详情**；未来可按 Activity 拆分，保持公开 ID 与 URL 不变。
- 从一个经审核的**逻辑模型及同一批准批次**生成上述文件，在同一个 PR／部署快照发布；对跨文件外键、版本一致性和回滚做自动校验。即使文件拆分，也不必建立复杂多服务系统。
- 不对 Google Sheet 直接在线读取、不自动同步、不把研究 Source 原样公开、不将媒体/截图有 URL 当作转载许可。
- **性能门槛仅属待实测建议**：可试以压缩传输后的 catalog 约 300 KiB 为优化目标，约 500 KiB 复查，约 1 MiB 优先考虑进一步分片；这些不是 GitHub/浏览器硬限制，亦未被批准为发行门禁。以真实经审批字段或隔离合成测试数据在 PC/iPhone 上验证首次请求、缓存命中、解析、DOM 卡片数与交互。
- 详情拆分、具体 `schemaVersion`、缓存与版本 manifest、文件数量、加载失败回退机制仍需最终确定。

## 8. 仍未批准和禁止自动执行的事项

1. **正式公开字段契约**：每类对象必填/可选字段、活动分类最终词表、全国共通机制精确表达、源关联与媒体许可。
2. **有效日期的数据表达**：连续范围＋排除日、日期集合、周几规则、Session 展开及变更史；需要先统一日期精度、时区/JST 和跨年边界。
3. **展示优先级两档的明确判据**、同级五十音读音键及排序测试。
4. **动态计数和状态汇总校验器**、异地同日、部分取消、全国共通、重复公告、跨月改期的边界用例。
5. **URL 兼容及前端迁移**：旧演示直链、`from`、筛选条件、返回按钮、加载失败／空态与无效 ID。
6. **方案 C 物理设计与容量实测**：确定 catalog/detail 分割、版本一致性、缓存、文件大小目标。
7. **首批正式内容**：筛选候选 → 原始公开资料逐项核查 → 维护者逐项审批 → 单独 PR → Pages / PC / iPhone 验收。研究库有项目不代表已取得网站发布许可。
