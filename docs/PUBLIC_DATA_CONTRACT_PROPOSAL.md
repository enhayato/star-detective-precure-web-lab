# 《探Q活动回忆档案馆》｜正式公开数据接入前审查与候选契约 V0.1

> **性质（2026-11-21 JST）：仅供用户审核的架构提案，不是已批准 schema、正式数据、发布许可或实施计划。** 不赋予内部研究记录对外发布资格，也不自动同步 Google Sheets/Docs 或任何 GitHub Pages 数据。后续需分别批准公开收录范围、计数单位、字段模型、发布门禁、首批内容和前端迁移。
>
> **公开仓库边界：**本文件只描述抽象模型和核查规则，不复制内部研究项目明细、未获准资料、审计备注、研究库 URL 或内部导出数据。权威研究库及其审核结论不以本 GitHub 文件为准。

## 一、已核对的工程事实

### 1. 网站当前原型

- \`data/events-demo.json\` 是 \`schemaVersion:1\` 静态演示文件，只有一条2026-10-15新宿 Staff Talk 示例。其公开公告、时刻和图片权限仍未完成独立发布级复核。
- 日历 \`index.html\`、地图 \`map.html\`、档案 \`archive.html\`、纪念册 \`event.html\` 均读取同一个 \`events[]\`。一个条目同时包含 \`id\`、标题、\`start/end\`、\`prefecture\`、\`pref/muni\`、场地、类别及简介。
- 日历与档案目前通过 \`e.start <= 查询区间终点 && e.end >= 查询区间起点\` 做日期重叠判断；日历圆点和地图高亮也来自同一条目。档案显示数量等于当前符合筛选的 JSON 条目数。纪念册 \`?id=\` 直达某一个 JSON 条目。
- 对单日单地演示记录，这种简化模型可以工作；它**不能自动正确表达**巡回项目、多会场、同日多场、仅周末举行、休馆日、取消活动、线上活动和公布日与举办日的差异。
- 当前日历面向2026年；地区在日历和档案仅区分东京都／其他，地图全国支持47府县、东京二级支持62区市町村。筛选类别当前仅为 \`staff_talk\`／\`other\`。旧详情 URL 和跨页 \`from=calendar|map|archive\` 返回逻辑已上线，迁移时必须维持兼容。

### 2. 内部权威研究库的只读结构比对

2026-11-21（JST）只读核对了内部 Google Sheets 的 metadata、九张表的名称，并对主要标签表读取限定范围表头及少量结构样本，**未全表核查、未核证全部原始 URL、未修改任何单元格**。

| 研究层 | 已存在的职能 | 直接导入网站的错误假设 |
| --- | --- | --- |
| \`Projects\` | 企划／合作项目，含范围、对外公告与实施跨度、原始来源、研究分类及未决事项 | 一个 Project 就等于一个日期、一处场地或一场活动 |
| \`Milestones\` | 公布、补充公布、实施、归档等时间节点，含日期性质、精度及来源关系 | 一个 Milestone 就等于一场演出；公布日就是举办日 |
| \`Sources\` | 来源主体、原始 URL、网页发表日、事件日、来源性质、核查程度和限制 | 一手来源等级就表示全文已核查，或网页图片可转载 |
| \`Research Control\`、审计类标签 | 研究治理、追查问题、完整性与覆盖记录 | 这些内审字段都适合公开展示给普通粉丝 |

**结构性缺口：**研究中的「企划—公告／执行节点—证据」并非完整、规范化的「每场对外活动与实际开放日／场地／场次」公开日程。即使项目有执行起止日，也不能认定中间每一天营业，亦不能认定每个会场／场次都已被逐条调查。

## 二、候选公开数据模型：研究事实与粉丝浏览单位分离

以下表是**待批准的概念层**，不是可以直接向前端导入的最终 JSON schema，也不是新增的真实数据记录。

| 对象 | 候选粒度、关系 | 公开字段候选（必须有支持证据） |
| --- | --- | --- |
| \`Activity\` 活动主档 | 访客可识别的同一主题活动或巡回企划；一个活动可有多个举办记录 | 稳定公开 \`activityId\`、名称、类别、获准公开的简介 |
| \`Occurrence\` 举办单位 | 一个确切场地／地区的举办记录，具有经核实的开放日程；属于一个 Activity | \`occurrenceId\`、父活动、举办日程、场地名、行政区、来源引用 |
| \`Session\` 个别场次（可选） | 同一举办单位下可区分的公演／座谈／见面会；不是每种活动都有 | \`sessionId\`、父举办单位、日期、来源确证时的开始时间、场次说明 |
| \`Announcement\` 公告／变更 | 首发、追加公布、日期变更、取消等公开信息节点；与活动或举办单位关联 | 公告日期（有精确证据时）、公告性质、所指对象、原始来源 |
| \`Source\` 对外可见的核证来源 | 对某个公开断言的直接支持关系，而非内部 Sources 表的全部拷贝 | URL、标题、发布主体、网页发布日期、被支持的内容 |
| \`Media\` 获准图片（可选） | 明确证实本站可展示或再利用的图片／海报 | 素材用途、归属、可用性或许可依据；缺许可则不展示 |

**ID 设计建议：**网站公开主键应独立于研究库的内部 Project/Milestone/Source ID，并保持长期稳定。内部关联可留在不发布的转换记录里。当前演示 ID \`sample-staff-talk-20261015\` 的直达链接需有明确向后兼容方案；不能简单删除或悄悄映射到其他活动。

### 日期与地点的规范性约束

1. **举办日 vs 公告日：**公开日历和当前地图应以已核实的**实际举办日期**为筛选依据，而不是首次公告日、补充公告日、资料发现日或网页核查日。未来的时间演化地图是否使用公告轴仍是独立待批准项目。
2. **不连续开放日：**起止日期只表示跨度，不证明中间所有日期均可参与。发生休馆、只有周末、指定日公演等情况时，必须表达有证据的实际日期集合、多个连续区间，或等价的日程方式。禁止把休业日错误点亮。
3. **一日多场：**一日两场不等于两个独立商业联动企划。是否给一场公演单独卡片，尚需审议；可以保留活动数、举办单位数和场次数三个层级。
4. **跨地点：**一个巡回企划的不同城市应有不同举办记录；不能把某一城市的日期和具体运营方断言外推到另一城市。
5. **线上／全国：**线上项目或宣传触达全国不等于47府县均有线下举办活动。地点缺失、地区仅有大致范围时不得为了地图着色虚构行政编码。
6. **跨年：**可以保留2027年结束的真实档期，但2026年日历只显示与2026年相交的实际举办日期；不能把正式结束日改成2026-12-31。
7. **日期精度与缺失：**内部仅知月份或模糊日期时，不能自动补成月初、月底、第一天或预计日。时间、票价、出演者不明时不补造。
8. **取消／未实施：**已公布、待举办、已实施、取消／延期或修改（具备可靠证据时）必须分别处理。本站是历史回忆档案，不得将仅有事前公告的活动直接宣布已经举行。
9. **证据双日期：**页面首次公布日、网页更新日、实际活动日、研究发现日、复核日是不同口径，不能互换。仅能阅读搜索摘要或索引的来源，不能被自动视为全文已经验证。
10. **分类与行政区：**研究库的商业关系 A/B/C/D/E 不等于粉丝网站的活动类别；类别映射和代码清单需独立批准。东京二级与全国一级需要合法且可核实的地区编码，不额外声称其他46府县有二级地图。

### 数量解释建议（未批准）

| 指标 | 候选计数单位 | 禁止替代的数值 |
| --- | --- | --- |
| 活动数 | 当前条件下有至少一个通过发布审核的举办记录的唯一 \`activityId\` | 内部 Project 数、公告数 |
| 举办记录数 | 匹配日期／地区的唯一 \`occurrenceId\` | 展期天数、主活动数 |
| 个别场次数 | 被一手或足够强的公开证据明确区分的 \`sessionId\` | 场馆可容纳人数、推测的每天举办次数 |
| 有记录地区数 | 按当前日期及类别过滤后，拥有可发布举办记录的不同地区编码数 | 全国实际覆盖率、售票量、商业影响 |

**具体卡片显示层级及文字标签仍待批准。** 现有 \`events.length\` 只能数原型条目，不能在多地、多场正式数据导入后默认称作「活动数」。

## 三、拟议发布视图和工程迁移步骤（均未实施）

1. **保留演示数据：**不要覆盖 \`data/events-demo.json\`，更不能把研究库直接整体导出并放在 GitHub Pages。所有未来正式数据必须通过单独批准的公开视图。
2. **候选新文件：**将来可以考虑 \`data/events-public.json\` 或等效静态资源、独立 \`schemaVersion\` 和版本化发布快照；**本次只提出名称，不创建文件，不定义最终字段结构。**
3. **非公开的制作层：**研究记录与公开数据之间需要人工核查/对照、生成独立公开 ID、断言—来源关系、日期和场次归并、字段剔除及回滚说明；这层不随网站公开。
4. **按批发布：**经用户逐条确认后，使用独立 Branch → 中文 PR → 用户合并 → Pages 部署 → PC/iPhone 验收。内部研究库和公开站点必须仍有清晰的权威关系；未经审批不做自动同步。
5. **改动前端必须显式迁移：**目前日历、地图、档案和纪念册对 \`events[]\` 的读取、日期区间和类别是硬编码。不能简单更换 fetch URL；至少要先批准：实际开放日判断、地方筛选、展示计数、活动详情层级、类别字典、缺地点降级策略和旧 URL 兼容。
6. **素材原则：**能公开访问的海报／照片不天然具备再发布授权。未获证的素材不打包、不热链、不改用生成图冒充现场图片。
7. **演示状态文案：**一旦引入正式资料，四页当前的「演示档案」「一条记录」以及关于本站的原型说明也必须同步审查，避免新旧数据状态相互矛盾。
8. **只把经核准的公开来源放上网站：**不能直接显示所有研究来源、内审核查意见、项目合作推论或无法核证的来源链接。公开引用应关联支持的事实，而不是装饰性「官方来源」标签。

## 四、正式发布的候选审核门禁

**证据门禁：**每条待发布断言（名称、举办地、举办日期、场次、实际实施、取消／延期、出演等）有可追溯的来源；标明正文已读、仅见摘要、无法访问、何时复核以及来源更新/相互冲突。研究来源评级 A 也不自动满足逐句核证。

**建模门禁：**明确 Activity→Occurrence→Session 的关系和多对多来源引用；唯一 ID 及外键有效；同一企划跨会场不重复算企划；多次公告不被重复算举办活动；明确时间区间是否真正连续开放。

**安全门禁：**只输出获准公开字段；不发布研究内审信息、商业推断、隐私资料或未授权图片；日期、行政编码、名称与来源一致；对未知值使用明确未知/暂不展示，不以零或空数组伪装为确证不存在。

**提交门禁：**每次发布标记候选→事实核查通过→用户批准→公开 PR→合并与部署验收的具体状态；保留变更前版本及退回方案；不能用一次全库结构审计 PASS 替代逐条公开资料审查。

### 必测的边界情景（抽象测试用例，非真实活动声明）

- 单日单地一场；同日同馆两场；同巡回企划分布多个城市。
- 展会跨月／跨年；休业日；只在周末开放。
- 事前公告但尚未实际举办；举办后补充报道；延期／取消。
- 全国线上合作；地区模糊；东京二级正确、其他府县二级尚不可用。
- 研究材料中出现多次公告，来源日期与活动日期不一致。
- 网页只见搜索摘要、图片再利用条件未知；来源链接失效。
- 分类未知、重复 ID、空数据、日期精度不足、缺场地／行政代码。
- 日历／地图／档案的数值按约定单位去重，且颜色只意味着有已收录活动。
- 旧演示 \`?id=\` 直达、过滤 URL、纪念册 \`from=\` 返回、加载失败态不回归。

## 五、需要用户另外批准的设计决策

| 决策 | 本次建议（**不是既成协议**） | 阻断原因 |
| --- | --- | --- |
| 收录范畴 | 聚焦已发生且可追溯的探Q公开线下活动；线上和纯商品促销分别讨论 | 不等于内部商业联动研究的全覆盖范围 |
| 记录粒度 | Activity＋Occurrence，必要时细分 Session | 决定多地、多场去重和详情页面 |
| 实际开放日语义 | 不连续日程需要明确日期集合或分段 | 当前单一 \`start/end\` 会误亮休业日 |
| 公开类别 | 面向粉丝的易懂类别，不照搬研究 A/B/C/D/E | 影响日历/地图/档案现有类型筛选 |
| 来源门槛 | 断言级证据核验＋核查限制；可公开 URL；图片另核 | 一手身份不等于正文及授权确认 |
| ID 与详情 | 公共 ID 不使用研究内部 ID；旧演示直链不丢失 | 影响书签、返回、同企划多个举办记录 |
| 数据同步 | 先人工审核的静态快照与 PR，不自动连接研究 Sheet | 避免内部资料外泄、批量错误与版本漂移 |
| 首批真实数据 | 少量证据完整、场次清晰、用户逐项审核后发布 | 研究已入库不等于网站可直接公开 |

**审批建议：**本轮仅批准把本方案归档为可讨论的候选，不等于批准字段、数据导入、发布时间、对外收录口径或任何新代码。讨论并确定上述阻断决策后，再设正式公开 schema／验证器和首批试导入方案；实施前取得明确授权。
